# @sparkelf/dsh-dataops-account

DataOps identity for the DSH account launcher.

DSH in a DataOps workspace has no DeepSeek account: the portal authenticated the
operator, and the workbench iframe receives that identity as presentation data.
This plugin shadows the official `settings.launcher` slot entry so the sidebar
foot shows the DataOps role badge and label, and the account menu offers only
Settings and Feedback — the unusable DeepSeek sign-in row is gone by
construction rather than deleted from the DOM after render.

## Identity handshake

The portal posts on every iframe load, repeats the post until the frame
acknowledges it, and also answers a request the plugin sends once its `message`
listener is installed. The payload carries presentation data only:

```json
{
  "type": "dataops:user",
  "version": 1,
  "user": {
    "id": "260afb31-f8d9-44ba-b161-2a9bfe283a79",
    "username": "admin",
    "displayName": "超级管理员",
    "avatarUrl": "data:image/svg+xml;base64,..."
  }
}
```

DataOps owns the label and the badge: today `displayName` is the user's primary
role name and `avatarUrl` is an inline SVG badge generated by the backend. The
plugin displays those two fields; it does not derive roles from `roles[]` and
does not load remote photos. Only `data:image/` and `blob:` URLs are accepted,
so an unreachable external URL cannot replace the badge with a blank square. A
missing or broken badge falls back to the label's first grapheme on the DataOps
blue disc (`超` for 超级管理员).

The plugin accepts the record only from `window.parent` and never treats it as
authorization. The last record is cached in the iframe origin's `localStorage`
so a reload or a second tab paints the last known role immediately, and the
state is mirrored to `document.documentElement.dataset` plus
`window.__DATAOPS_USER__` for diagnosis.

The store itself lives on `window.__DATAOPS_ACCOUNT_STORE__` so a second
evaluation of the client bundle (HMR) observes the same record instead of
starting a second, permanently pending store.
## Feedback dialog

The account menu's Feedback row opens a dialog in the DSH frame instead of
navigating to an external form. The dialog offers a category (feature / problem
/ other), required details (trimmed, at most 2000 characters), and an optional
contact line (at most 200 characters). Submission travels over the same
parent/child channel as identity:

```text
DSH  -> parent  { type: 'dataops:feedback-submit', requestId, payload: { category, content, contact, pageUrl, user } }
portal -> DSH   { type: 'dataops:feedback-result', requestId, ok: true, id }
                { type: 'dataops:feedback-result', requestId, ok: false, error }
```

The portal keeps the only DataOps credential: it calls
`POST /api/feedback` with the current bearer token, and the backend derives the
author from that token rather than trusting `user`. The plugin waits 15 seconds
per submission, maps `timeout` / `429` / invalid input to localized copy, and
shows the backend's message for other failures. A successful submit closes the
dialog and shows a toast; no popup or external navigation is involved.
